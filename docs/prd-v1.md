## 0. القرارات المحسومة

| القرار | الاختيار |
|---|---|
| Stack | **Next.js (App Router) + Supabase** — ويب أولاً، بعدين Expo/React Native على نفس الـAPI والـAuth |
| التواصل في V1 | **شات داخل المنصة** |
| التوثيق | **طبقتين**: موثّق أساسي (OTP) + موثّق أوراق (مراجعة يدوية) |
| نموذج الربح | **مجاني بالكامل في V1**. الدفع والـescrow في V2 |
| تكامل هيئة الدواء | لا يوجد — المنصة كلها **قبل** التسجيل الرسمي |
| التموضع القانوني | مؤجل — بس V1 اتكتب بحيث ميقفلش أي باب (شوف §9) |
| الاسم | **DawaMudir** — من "دوا" + "مدير"، واضح للفئة بدون ما يبقى اسم عام (شوف §0.1) |

### 0.1 قرار الاسم والدومين

اتعمل نقاش حقيقي (Claude + Codex/GPT كـ second opinion) على 3 مرشحين، وبعدين **تحقق فعلي** بـwhois:

| الاسم | الفكرة | `.com` فعلياً | القرار |
|---|---|---|---|
| Modeerak (مديرك) | أقوى صوتياً بالعربي | **متسجل** (فبراير 2026) | استبعاد |
| Wasetak (وسيطك) | يغطي الطرفين، بس قريب من "وسيط/سمسار" | **متسجل** (2024) | استبعاد |
| **DawaMudir** | مركّب واضح للفئة، أقل عمومية من "pharmacy jobs" | **متاح** | **✅ الاختيار** |

**الدومين:** `dawamudir.com` متاح فعلياً (~10-15$/سنة). لازم يتسجل بسرعة قبل الإطلاق العام — دومينات زي دي بتتاخد سريع لما تتداول في نقاش عام.
**ملاحظة:** `.app` مانتحققش منه فعلياً (whois اتحجب في بيئة الفحص) — يتأكد منه يدوي عند التسجيل كـbackup.

**الهدف الوحيد لـV1:** أجمع أكبر عدد صيادلة وأصحاب صيدليات موثّقين في مكان واحد، وأخليهم يتواصلوا جوه المنصة.

**مقياس النجاح:** عدد الحسابات الموثّقة بأوراق، وعدد المحادثات اللي بيتأكد إنها وصلت لاتفاق.

## 1. المستخدمون

**أ. صاحب الصيدلية (Owner)** — عنده صيدلية واحدة أو أكتر، محتاج مدير مسجَّل. ألمه: الوقت والنصب. هو الطرف اللي هيدفع في V2.

**ب. الصيدلي (Pharmacist)** — عايز يسجل مدير مقابل مرتب. أغلبهم خريجين جدد قبل/بعد التكليف، أو صيادلة شغالين عايزين دخل إضافي. ألمه: المكاتب بتاخد نص حقه، ومش عارف السعر الصح، وخايف من المسؤولية القانونية.

**ج. الأدمن (إنت)** — مراجعة الأوراق، إدارة البلاغات.

> ملاحظة: نفس الشخص ممكن يكون الاتنين (صيدلي عنده صيدلية وبيدور على مدير). الـrole مش حقل واحد — لازم يكون **قدرات** على الحساب، مش نوع.

## 3. نموذج التوثيق (الطبقتين)

ده قلب المنتج — أكبر شكوى في الجروب هي "أرقام وهمية وأسماء دكاترة وهمية بنفس الموبايل".

| الطبقة | الشرط | الميزة |
|---|---|---|
| **موثّق أساسي** 🔵 | OTP على موبايل مصري + اسم | يقدر ينشر إعلان واحد، ويشوف ويتراسل — **من غير ما يستنى المراجعة** |
| **موثّق أوراق** ✅ | مزاولة المهنة + الرقم القومي (للصيدلي) · ترخيص الصيدلية + الرقم القومي (للصاحب) — مراجعة يدوية | بادج، أولوية في نتايج البحث، إعلانات أكتر، والرد بيوصل أسرع |

**SLA المراجعة:** التزام واضح بمراجعة الأوراق خلال **24-48 ساعة**، ويتعرض للمستخدم كـ"جاري المراجعة" مش شاشة انتظار مقفولة. القرار (بعد نقاش الاسكوب): المراجعة اليدوية تفضل من اليوم الأول — إلغاؤها بيخلي المنصة زي الجروب بالظبط في أول يوم، وده بيهد كل قصة الثقة. الحل مش إلغاء المراجعة، الحل إن الموثّق أساسي **يقدر يستخدم المنصة كاملة** وهو مستني، والبادج بس هو اللي بياخد وقت.

**قواعد مضادة للتزوير — لازم من اليوم الأول:**
- الموبايل **unique** على مستوى الحسابات
- **رصد إعادة استخدام الرقم**: لو نفس الموبايل ظهر في متن أكتر من إعلان أو بروفايل → flag أوتوماتيك للأدمن
- حد أقصى للإعلانات النشطة: 1 لغير الموثّق، 3 للموثّق أوراق
- رقم المزاولة **unique** بعد الموافقة
- الصور بتتخزن في bucket **خاص** — signed URLs بصلاحية قصيرة، والرقم القومي **مايتعرضش لأي حد غير الأدمن أبداً**، ولا بيتنشر في أي مكان

## 4. الداتا موديل (Postgres / Supabase)

```sql
-- lookups
governorates      (id, name_ar, name_en)
districts         (id, governorate_id, name_ar)

-- الحساب
profiles (
  id                uuid pk references auth.users,
  full_name         text,
  phone             text unique not null,
  governorate_id    int references governorates,
  district_id       int references districts,
  is_pharmacist     bool default false,
  is_owner          bool default false,
  verification_tier text check (in ('basic','documents')) default 'basic',
  avatar_url        text,
  is_banned         bool default false,
  created_at        timestamptz
)

-- بيانات الصيدلي
pharmacist_details (
  profile_id            uuid pk references profiles,
  license_number        text unique,          -- مزاولة المهنة، بعد الموافقة
  graduation_year       int,
  takleef_status        text,                 -- لسه/جاي/خلص/ملغي
  is_available          bool default true,
  open_to_durations     text[],               -- permanent | temporary
  open_to_attendance    text[],               -- with | without
  accepts_schedule      bool,                 -- بجدول؟
  accepts_imported      bool,                 -- بمستورد؟
  expected_salary_min   int,
  expected_salary_max   int,
  preferred_governorates int[],
  bio                   text
)

-- الصيدلية
pharmacies (
  id                 uuid pk,
  owner_profile_id   uuid references profiles,
  name               text,
  license_number     text,
  governorate_id     int, district_id int,
  address_text       text,
  has_schedule       bool,                    -- عندها جدول؟
  sells_imported     bool,                    -- بتتعامل بمستورد؟
  clean_record       bool,                    -- إقرار: مفيش مخالفات
  created_at         timestamptz
)

-- الإعلانات (الطرفين في جدول واحد)
listings (
  id             uuid pk,
  kind           text check (in ('manager_wanted','manager_available')),
  author_id      uuid references profiles,
  pharmacy_id    uuid references pharmacies,   -- لـmanager_wanted فقط
  duration_type  text check (in ('permanent','temporary')),
  duration_months int,                          -- لو temporary
  attendance     text check (in ('with','without')),
  schedule       text check (in ('with','without')),
  imported       text check (in ('with','without')),
  governorate_id int, district_id int,
  salary_amount  int,                           -- nullable
  notes          text,
  status         text check (in ('active','paused','closed')) default 'active',
  expires_at     timestamptz,                   -- 30 يوم، بتجديد بضغطة
  created_at     timestamptz
)

-- التوثيق
verification_documents (
  id, profile_id, pharmacy_id,
  doc_type    text,   -- license | national_id | pharmacy_license
  storage_path text,
  status      text check (in ('pending','approved','rejected')),
  review_note text, reviewed_by uuid, reviewed_at timestamptz
)

-- الشات
conversations (id, listing_id, participant_a, participant_b, last_message_at, unique(listing_id,participant_a,participant_b))
messages      (id, conversation_id, sender_id, body, created_at, read_at, contains_phone bool)

-- الاتفاق — الجزء الأهم استراتيجياً
deals (
  id, conversation_id, listing_id,
  owner_id, pharmacist_id,
  agreed_salary   int,
  duration_type   text, duration_months int,
  start_date      date,
  confirmed_by_owner      bool default false,
  confirmed_by_pharmacist bool default false,
  status text check (in ('pending','confirmed','cancelled','completed'))
)

reviews (id, deal_id, author_id, target_id, rating int, comment text)
reports (id, reporter_id, target_type, target_id, reason, status)
```

### ليه جدول `deals` في V1 وهو مجاني؟
لأنه هو **نفس الـobject** اللي هيتحول لـescrow في V2. لو V1 خلص من غيره، هتلاقي نفسك عندك منصة مفيهاش أي داتا عن الأسعار الحقيقية ولا أي أساس للتقييمات، وV2 هيبقى rewrite. في V1 هو مجرد فورم بسيط: "تم الاتفاق؟ المرتب كام؟ المدة؟" والطرفين يأكدوا. من الداتا دي بتطلع:
- **متوسط السعر بالمحافظة ونوع الاتفاق** → أقوى محتوى تسويقي عندك، ومحدش تاني عنده
- **تريجر التقييم** (تقييم من غير صفقة = تقييمات وهمية)
- **الـtrack record** بتاع كل حساب

**نقطة خلاف اتناقشت (Codex اقترح تأجيل الجدول كله لـv1.1 عشان مفيش monetization ولا enforcement لسه):** القرار النهائي **مش الإلغاء** — الجدول نفسه فورم اتنين checkbox، مش نظام. الفرق بسيط: **السكيما تتعمل في M0 زي ما هي**، لكن لو الوقت ضغط في M2/M3، **واجهة "تم الاتفاق" (الزرار + الفورم) تتأجل لـv1.1** بدل ما تتبني في M5. اللي متأجلش هو العمود، اللي ممكن يتأجل هو الزرار.

### RLS (Supabase)
- `profiles`: قراءة عامة للحقول العامة فقط — **الموبايل مش في الـpublic view**. اعمل `public_profiles` view وامنع الوصول للجدول الأصلي.
- `verification_documents`: صاحبها + الأدمن فقط. الـstorage bucket **private**.
- `messages`: أطراف المحادثة فقط.
- `deals`: الطرفين فقط. الأدمن يقرأ aggregate بس.
- `pharmacies`: العنوان التفصيلي يظهر بعد بدء المحادثة، والمحافظة/المركز عام.

## 5. الشاشات

**عام (بدون تسجيل — مهم للـSEO):**
- الصفحة الرئيسية
- تصفح الصيادلة المتاحين · تصفح الوظايف (مطلوب مدير)
- صفحة إعلان (بدون بيانات تواصل — "سجّل عشان تتواصل")
- **صفحات محافظات**: `/مدير-صيدلية/طنطا` — دي اللي هتجيب لك ترافيك مجاني. **القرار بعد النقاش:** التمبلت/الراوت يتعمل في M2 زي ما هو مخطط، لكن **النشر (index) يبقى تدريجي مش دفعة واحدة على الـ27 محافظة**. يبدأ بس بالمحافظات اللي فيها كثافة إعلانات حقيقية (القاهرة، الجيزة، الإسكندرية، المنصورة، طنطا، الزقازيق)، والباقي `noindex` لحد ما يبقى فيها إعلانات كفاية — صفحة فاضية بتضر الـSEO أكتر ما تفيده.
- **دليل الإجراءات**: الأوراق المطلوبة · خطوات المنصة · إزاي تعمل ترك · صيغة جواب الترك · مسؤوليات المدير القانونية

**بعد التسجيل:**
- اختيار الدور → OTP → ويزارد البروفايل → رفع الأوراق (يقدر يتخطاه ويكمله بعدين)
- لوحتي: إعلاناتي · محادثاتي · حالة التوثيق · صيدلياتي
- الشات + زرار "تم الاتفاق"

**الأدمن:**
- طابور مراجعة الأوراق (موافقة/رفض بسبب)
- البلاغات · الحسابات المفلاجة (تكرار أرقام) · إحصائيات

## 6. الشات وسؤال الواتساب

الناس في مصر هتحاول تنقل الكلام على واتساب من أول رسالة. **متحظرش الأرقام** — ده هيكسّر الاستخدام. بدل كده:
1. الشات يبقى سريع وفيه إشعارات فعلية (بريد + Web Push، وفي V2 push على الأبلكيشن)
2. سجّل `contains_phone` على الرسالة للتحليل بس
3. بعد أول تبادل رسايل بيوم، نوتيفيكيشن: **"وصلتوا لاتفاق؟ سجّله عشان تقيّم بعضكم"**
4. التقييم مايتعملش غير من خلال صفقة مسجلة — ده الحافز الحقيقي إن الاتفاق يترجّع للمنصة

## 7. البداية الباردة (Cold start)

**اجمع العرض قبل الطلب.** صاحب الصيدلية لو دخل ولقى صفر صيادلة هيمشي وميرجعش؛ الصيدلي لو دخل ولقى صفر وظايف بيرفع أوراقه ويستنى.

1. **أسبوع 1–2:** بوستات في الجروب موجهة للصيادلة: "وثّق أوراقك مجاناً واظهر لأصحاب الصيدليات — من غير مكاتب ومن غير عمولة". العرض بسيط: **بادج مجاني وظهور في نتايج البحث**.
2. **بروفايل عام قابل للمشاركة** لكل صيدلي موثّق — لينك ينزّله هو بنفسه في الجروب بدل ما يكتب بوست. ده أهم loop عندك: هو بيسوّق لنفسك.
3. **أسبوع 3+:** لما يبقى فيه 100+ صيدلي موثّق، ابدأ تروّج لأصحاب الصيدليات برقم حقيقي: "50 صيدلي موثّق في الغربية دلوقتي".
4. **متعملش scraping للجروب** — بيانات شخصية، وده مخالف لسياسات فيسبوك ولقانون حماية البيانات المصري 151/2018، وأسوأ حاجة إنه هيحرقك مع نفس الجمهور اللي محتاجه.

## 8. الملاحظات التقنية

- **الـOTP**: Supabase Phone Auth محتاج مزود SMS. Twilio للأرقام المصرية غالي نسبياً — قارن مع مزود محلي (SMS Misr / Victory Link) أو ابدأ بـ**WhatsApp OTP** عبر Cloud API (أرخص، وكل الجمهور عليه). الـauth abstraction تفضل Supabase في كل الحالات.
- **RTL**: `dir="rtl"` من الجذر، خط IBM Plex Sans Arabic أو Cairo، أرقام عربية-غربية (123)، وانتبه للـlogical properties في Tailwind (`ps-`/`pe-` مش `pl-`/`pr-`).
- **الصور**: ضغط قبل الرفع client-side، والمستندات PDF/صورة بحد أقصى 5MB.
- **جاهزية الأبلكيشن**: كل شيء يمر بـSupabase client + Postgres RPC/Edge Functions — من غير أي business logic في Next.js server actions تخص الدومين، عشان Expo بعدين يستدعي نفس الحاجة.

## 9. الأبواب اللي سيبناها مفتوحة (قرار التموضع)

إنت مأجّل قرار "سوق توظيف حقيقي ولا وسيط للسوق بشكله الحالي". عشان القرار ده يفضل مفتوح:
- الفلاتر بتوصف الواقع (`attendance: with|without`) من غير ما المنصة **تروّج** لـ"بدون حضور" في الماركتنج
- الشروط والأحكام تقول بوضوح: المنصة **تعارف فقط**، مش طرف في أي اتفاق، ومش بتقوم بالتسجيل لدى الهيئة
- صفحات الدليل تشرح **مسؤوليات المدير القانونية** بصراحة — ده بيحميك، وكمان بيبني الثقة اللي هي أساس المنتج كله
- استشارة محامٍ قبل الإطلاق العام — مش قبل الـMVP

## 10. خطة التنفيذ

| المرحلة | المحتوى | تقدير (سولو، دوام جزئي) |
|---|---|---|
| M0 | إعداد المشروع، Supabase، سكيما، RTL، ديزاين سيستم | 3–4 أيام |
| M1 | Auth + OTP + بروفايلات + رفع أوراق | ~1 أسبوع |
| M2 | الإعلانات + البحث والفلاتر + صفحات المحافظات | ~1.5 أسبوع |
| M3 | الشات + الإشعارات | ~1 أسبوع |
| M4 | لوحة الأدمن + مكافحة الاحتيال | 4–5 أيام |
| M5 | `deals` + التقييمات + صفحات الدليل | ~1 أسبوع |
| M6 | اختبار مع 10 مستخدمين حقيقيين، ثم الإطلاق في الجروب | 3–4 أيام |

**الإجمالي: ~6 أسابيع.** لو عايز تختصر: M5 ممكن يتأجل بعد الإطلاق **ما عدا جدول `deals`** — الجدول نفسه لازم يتعمل في M0 حتى لو الواجهة اتأجلت.
